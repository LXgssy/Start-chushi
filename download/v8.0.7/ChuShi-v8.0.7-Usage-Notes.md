# ChuShi v8.0.7 · 轮询租约——命令队列唯一消费者

## 这轮修的是什么

你上一轮的证据（cmdTrace 里 9 条命令全部 `ok:true`、面板显示已连接 v8.0.6、但控制全部无效、横幅亮「音乐桥未执行命令」）指向一个结论：

- `ok:true` 只代表 hub 收到了命令（页面侧 POST 轨迹）；
- 桥的状态通道活着（歌名/进度/歌词都在实时刷新）→ 桥的轮询循环在跑；
- 但桥的执行回执**从未出现** → 桥每次去取命令，队列都是**空的**；
- hub 的 `GET /api/cmd` 是**排空式先到先得** → **有第二个轮询者在抢命令**。

最典型的第二个轮询者：**网易云残留进程**（网易云退出不干净是老毛病）里还跑着旧版桥的 JS；或者 BetterNCM 向多个进程注入了同一份 JS（防重入守卫只在单进程内有效）。命令被旧实例抢走后走旧版执行路径（在你这台 NCM 上全灭），回执字段也是旧格式/缺失——于是「POST 成功 + 面板在线 + 控制全死 + 无回执」四件事同时成立。

## v8.0.7 的修复

| 修复 | 说明 |
|---|---|
| **轮询租约（poller lease）** | hub 新增 `POST /api/poll` 认领端点：粘性持有者（TTL 4 秒，持有者沉默超时才许接管）。只有持有者能排空命令队列，非持有者被 hub 直接拦为空数组——**抢排在结构上不再可能**，不管第二个轮询者是谁（残留进程/多进程注入） |
| **桥侧执行轨迹全量透传** | `state.cmd.trace`（20 条环形）+ `who`（实例身份）+ `lease`（租约态）随 1Hz 状态上报。你在**浏览器**控制台执行 `__chushiMusicBridge.debug()` 就能看到**桥内部每一步**（收到命令→调用 InfLink→验证→降级到哪一路），诊断盲区永久消灭 |
| **双架构 hub 补齐** | 历代发布的 hub.dll 全是 x64-only，32 位网易云用户从未加载成功过（六代欠账）。本版恢复宪法：`hub.dll`=x86 主架 + `hub.dll.x64.dll`=x64 变体（BetterNCM 加载失败自动追加 `.x64.dll` 重试，与 InfLink-rs 同约定）。x86 构建用 `-DHUB_NO_SEH` 绕开了 llvm-mingw i686 后端崩溃（历史挂起项就此解决） |
| **持有者变更日志** | hub-log.txt 新增 `[poll] holder <- xxx` 行——如果真有残留进程反复尝试认领，日志里会现形 |

## 升级步骤（重要：必须杀干净进程）

1. **完全退出网易云**：不只是点右上角 ×——打开任务管理器，把所有 `CloudMusic.exe` / 网易云音乐相关进程**全部结束**（这一步就是治残留进程的，跳过 = 白升级）
2. 替换插件：只换 **`ChuShi-Music-Bridge-8.0.7.plugin`** 一个文件（歌词源 7.2.0 和 cshz 预设与 8.0.6 完全相同，**不需要重新导入预设**）
3. 启动网易云 → 刷新「初始」页 → 面板应显示 `已连接 · API v8.0.7`

## 验证

- 按播放/暂停/上下首/拖进度条
- 如果仍无效：浏览器控制台执行 `__chushiMusicBridge.debug()`，截图完整输出（现在包含 `cmdTrace`——桥侧执行轨迹、`who`——实例身份、`lease`——租约态）
  - `cmdTrace` 里**有条目** → 命令到达桥，看它走到哪一路失败（这正是下一层定位需要的信息）
  - `cmdTrace` **为空** + `lease:'standby'` → 有别的实例在当家（残留进程还在），回任务管理器杀进程
  - `lease:'legacy'` → hub 没升级成功（插件没换对）
- 也可以把网易云插件目录里 hub.dll 同目录的 `hub-log.txt` 发我，`[poll]` 行能直接看到几个实例在抢
